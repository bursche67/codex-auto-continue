# 从问题到 Skill

开发日期：2026-10-20。面向 Windows Codex 桌面版。

## 1. 原始问题

用户希望在睡觉期间，长任务因为额度不足中断后，能够在额度恢复时继续执行，不必醒来后手动输入“继续”。目标是等待正常额度恢复后继续已授权工作。

## 2. 先确认产品边界

查阅官方技能、聊天内定时任务和 App Server 文档，并使用应用提供的额度读取工具确认存在短周期及周额度窗口。由此确定：不能只按固定五小时重试，也不能把“窗口时间到了”当成额度已可用。

Skill 是执行规则，不能独立常驻，也无法在模型完全无法运行时自行唤醒。必须有调度机制。GitHub 中发现同类 CLI 自动恢复请求，但它不证明桌面版已经具备这一能力。

## 3. 用户选择的方案

经过两轮选择，锁定：

- 恢复 Codex 桌面版原聊天。
- 首版使用内置聊天 heartbeat，不先开发 Windows 后台程序。
- 每个聊天主动开启，默认每 15 分钟运行，不监督全部聊天。
- 验收保留真实限额恢复测试；未测试时不声称可靠实现。

选择这条路线是因为聊天内调度可以保留上下文，实施与维护工作较少。独立后台程序可在未来研究，但需要另行验证桌面连接、会话恢复和并发控制，首版没有实现。

## 4. 实现与一次修正

创建技能入口、UI 元数据、heartbeat 提示词模板及验证记录。开启时保存原目标、完成标准、进度与授权边界；通过提示词标记和准确的聊天绑定查找已有记录，重复开启更新同一记录。

首次调用创建工具时，缺少当前聊天目标参数，工具拒绝了请求。修正为 `destination=thread` 后创建成功。这个差异已写入技能，避免把“创建定时任务”误操作为新聊天中的独立任务。

通过工具暂停同一任务，读取保存状态确认 PAUSED，再重新启用并读取确认 ACTIVE。检查了 15 分钟间隔、原聊天绑定、技能标记以及仅一个启用记录。仅读取本地 TOML 作验证，未直接修改应用配置。

官方校验脚本需要 PyYAML。初次选用的运行时缺少依赖，随后改用本机已有且具备依赖的 Python 环境运行，格式校验通过；另外检查了 UI 元数据和引用文件。

## 5. 防止错误续跑的规则

任务是否完成以原目标的验收标准为准，不能因为上一轮有最终答复就判定整个任务完成。等待额度时保留定时任务；等待用户答复、审批或用户明确暂停时暂停监督。停止监督与中断正在运行的工作是两件事，不混为一谈。

用户的新指令优先，不启动同一目标的重复工作，不扩大权限、替用户审批或自动购买额度。正常可修复错误继续处理，无法自主解决的真实阻塞才停止并通知。

## 6. 已验证与尚未验证

已验证技能格式及应用配置生命周期。另创建了一次真实调度验收，计划在技能交付后首次有效唤醒时记录结果并暂停，但发布准备时还没有观察到该触发。

尚未验证额度耗尽后的完整恢复链路。它要求自然遇到限额，观察失败触发是否影响后续调度，再观察恢复后的原聊天续跑。没有通过故意耗尽额度来制造测试条件。

如果关键链路失败，正确结论是内置方案存在限制，需要进一步研究后台监控程序，不能将本项目宣传为已可靠恢复的无人值守工具。

## 7. 发布整理

将技能、使用说明和开发过程整理为可独立阅读的仓库。公开版本移除真实聊天 ID、本机路径和账户运行配置；使用通用提示词模板，不发布完整私人聊天记录。对外保留验证证据的类型与结果，并明确未完成的验收项。
